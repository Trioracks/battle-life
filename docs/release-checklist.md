# Публикация проверенного preview

## Однократная настройка владельцем

В `Trioracks/battle-life` откройте Settings → Pages → Build and deployment →
Source и выберите **GitHub Actions**. Доступность будущего адреса
`https://trioracks.github.io/battle-life/` подтверждает только успешная публикация.
Если Pages ещё не настроен, PR-проверки всё равно выполняются: configure-pages
и deploy-pages находятся исключительно в защищённой задаче deploy. Workflow
не включает Pages автоматически и не требует PAT. Используется штатный
`GITHUB_TOKEN` и OIDC; токены не добавляются в файлы репозитория.

## Каждый выпуск

- Создать ветку от актуального master, внести только публичные изменения и
  проверить [происхождение снимка](public-source-provenance.json). Полную
  сохранённую ветку и её историю не вливать.
- Выполнить [локальные проверки](public-preview.md): `npm ci`, `npm test`,
  source/new-history аудит, сборку, site-аудит и браузерный smoke собранного
  `dist/public-preview` в изолированном контексте. Записать SHA, результаты,
  размер артефакта и скриншоты вне артефакта/исходного дерева.
- Проверить отсутствие бинарного аудио, stems, Blender, архивов, секретов,
  локальных настроек и QA во всех новых коммитах, а не только в последнем дереве.
  Соблюсти бюджет 350 MiB всего / 95 MiB на файл. При превышении остановиться и
  согласовать изменение; не оптимизировать и не удалять молча.
- Получить независимое ревью и успешный `checks-build` на точном PR head SHA.
  Новое изменение после проверки требует нового прогона/ревью. Проверить
  профиль `public-preview`, notice об отключённой музыке/вокале, процедурные
  эффекты, сохранения, меню, квартиру, компьютер, браузер/форум/турнир,
  относительные ресурсы под `/battle-life/`, отсутствие ошибок загрузки.
- После одобрения merge в master запускает публикацию. Не force push и не
  переписывать историю. Manual `workflow_dispatch` публикует только master;
  другая ветка только проверяется. PR никогда не публикуется.
- Убедиться, что `checks-build` прошёл на новом master SHA, затем deploy
  завершился. Открыть URL из environment `github-pages`/summary, сравнить
  `release.json.revision`, SHA в меню и master SHA. Проверить загрузку страницы,
  квартиры и компьютера. Передать тестерам URL и SHA, собрать обратную связь
  по [чеклисту скриншотов](public-preview.md#тестерам).

Все официальные action закреплены полным SHA с комментарием версии. По
умолчанию разрешено только `contents: read`; только deploy получает
`pages: write` и `id-token: write`. Checkout не сохраняет credentials.
CI использует Node 24, Python 3.13 и закреплённый Playwright; локальное аудио
не является зависимостью. Загружается только `dist/public-preview`.

Отмена устаревших задач действует только в группе `pages-publication` задачи
deploy. Последняя проверка внутри этой группы, непосредственно перед
deploy-pages, сравнивает SHA артефакта с SHA события и текущим удалённым master.
Поэтому старый медленный build, завершившийся после новой публикации, будет
отклонён. При ошибке доступа к master проверка закрывается с ошибкой. Если
master успел измениться — дождаться проверки и публикации нового SHA.

## Откат и повторная публикация

Для отката создайте ветку от master, выполните `git revert <плохой-коммит>`
(для merge сначала определите правильного родителя), проверьте и проведите
обычный PR/review/merge. Это новый master SHA с восстановленным кодом; новая
сборка должна показывать этот SHA. Не возвращайте master через reset/force push.

Для повтора после инфраструктурной ошибки запустите workflow вручную на
актуальном master. Старый SHA не пройдёт финальную проверку. Если workflow
красный, сайт может оставаться на предыдущем успешном выпуске; проверяйте
фактический `release.json`, не считайте merge доказательством deployment.
Если ошибка в настройке Pages, владелец проверяет Source = GitHub Actions и
доступ environment, затем повторяет запуск. Сохранения игроков не очищаются.
